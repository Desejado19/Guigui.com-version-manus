# Inventário de persistência PostgreSQL do Guigui.com

**Estado:** em execução; inventário estático do código, sem consulta a bases de dados
**Objetivo:** identificar a fonte atual e a fonte de verdade desejada para os dados persistentes próprios da aplicação, e ordenar as fatias de migração.
**Escopo:** sete contextos de `CAPABILITY-MAP.md`; não altera runtime, schema ou dados.

## Método e limites da evidência

- Cada fluxo é rastreado por referências de código entre UI, API, serviços/adaptadores e migrations; uma tabela ou endpoint isolado não é considerado prova de persistência funcional.
- A inspeção é de código/schema. Não foram abertos ficheiros de dados JSON, `.env`, snapshots, registos de clientes ou conteúdo de backups; nenhuma base de dados foi consultada ou modificada.
- “Cobertura PostgreSQL” significa que o caminho de leitura/escrita observado usa a tabela indicada; não significa que uma migração de dados antigos ou reconciliação tenha sido executada.
- Fontes em memória e `localStorage` são separadas de dados duráveis. Configuração/segredos pertencem ao ambiente, conteúdo binário a um armazenamento de ficheiros e assets estáticos ao deploy.
- Os caminhos JSON são referências aos nomes usados pelo código. O conteúdo desses ficheiros não foi lido.

## Classificações

- **Negócio durável:** registos próprios necessários para a funcionalidade entre sessões.
- **Operacional/auditável:** execução, telemetria ou trilho de responsabilidade; definir retenção e acesso.
- **Temporário/derivado:** cache, estado de processo, métrica agregada ou estado de interface reconstruível.
- **Configuração de ambiente:** valores de runtime e segredos; não são registos de negócio nem devem ser migrados para tabelas.
- **Externo:** estado cuja fonte de verdade pertence a um fornecedor ou sistema externo.
- **Media binária / asset estático:** conteúdo de ficheiros ou artefactos do deploy; fora das tabelas de negócio, salvo metadados/propriedade/referências de media.

### Elementos de implementação transversais observados

- `server/runtimeStore.ts` fornece leitura/escrita JSON sob `GUIGUI_DATA_DIR`. `loadJson()` converte qualquer erro de leitura/parsing em fallback, ao passo que `loadJsonStrict()` só aceita fallback para ficheiro ausente. Cada consumidor desse helper é inventariado no respetivo contexto; não se assume que o fallback seja cache.
- `server.ts` continua a montar rotas e compor serviços. `CAPABILITY-MAP.md` confirma composição num único processo e proíbe inferir ownership modular apenas pela presença de diretórios.
- A configuração de base é opcional em `server/db.ts`, e health só marca degradação quando uma base configurada falha. Isto diverge da decisão aprovada de exigir base conectada em produção e deve ser resolvido antes de qualquer campanha com dados persistentes.

### Evidência de arquitetura da identidade

- O módulo `server/modules/identity-access/` tem camadas de domínio, aplicação, infraestrutura, HTTP e composição, mas a composição em `server/modules/identity-access/composition.ts` seleciona adapters e mantém partes da persistência JSON. A extração é parcial, não prova uma fonte PostgreSQL única.
- `server/modules/identity-access/infrastructure/jsonIdentityRepository.ts` referencia `auth.json`, `demo-passwords.json`, `password-reset-tokens.json` e `team-invitations.json`. Foram consultadas somente essas referências e as funções de código; os ficheiros de dados não foram abertos.
- `server/modules/identity-access/infrastructure/sessionRepository.ts` referencia `sessions.json`, grava em JSON mesmo com PostgreSQL configurado e muda as leituras/revogações para PostgreSQL quando a pool existe.
- O cookie é a sessão HTTP; o estado de utilizador em `localStorage` não entra na allowlist de sincronização e não substitui a autorização servidor.
